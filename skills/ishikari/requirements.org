The investigator judges each task once its report is written, and a trivial task skips every later ant.
- Trivial means all of: small, known scope (1-2 files, easy to find); one sensible way to do it, no design choice; one task that cannot be split. Docs or config only is a plus, not a must. A task that needed any question to the user is never trivial.
- The live investigator replies with trivial and trivialWhy. It gives the verdict once the report is written, before it designs or plans.
- The skill asks the user once to confirm the fast path. No runs the full plan with investigated set.
- On the fast path the main session edits on branch ishikari/<run>/fast in a worktree under the state folder, runs testCommand then checkCommand there, and fast-forwards main only when both pass. It checks first that the main checkout is on main and clean, never lands untested, and logs one "fast path landed" entry through ishikari.py.
- Escalation: more than 2 files, a design choice, more than one task, or a failing test or check a small fix does not clear. The edits are thrown away and the same investigator is told why and goes on to design and plan; ishikari-plan.js is passed escalated and logs a "fast path escalated" entry. The run then carries on without asking.

- product_spec.md replaces the investigation report. It holds two lists and nothing else: behaviours (B1, B2...), each as given / when / then, and invariants (I1, I2...), each written so an ant can check it. No goal, decisions log, facts or assumptions; the user's answers show up as the behaviours they led to.
- tech_spec.md replaces architecture.md: the architecture and the code's shape, with every spec id mapped to the part that delivers it.
- Both are for this task only, in the run's plans folder, never in the repo.
- Each worker plan names the spec ids it covers. ishikari-plan.js refuses the plans when an id has no plan, a plan covers none, or a plan names an id the product spec does not have.
- A task that changes no behaviour has invariants only.
- The trivial verdict comes after the product spec; a trivial task is built from it alone.
- Detectives check a task against its plan and the tech spec. The judge and jurors score the merged code against the product spec, id by id.
