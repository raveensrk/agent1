* Each Requirement must be an org mode heading
* A requirement file can be 1 file or multiple files
* Requirements can be scheduled.
If a requirement is written but becomes valid only after 2 weeks. =:SCHEDULED:= Property.
* Data format = =YYYY-MM-DD=
* Properties
Properties are optional for a small design. For larger design the following fields becomes mandatory.
** =:CREATED:= - date
** =:LAST_EDITED:= - date
** =:APPROVED:= - date
** =:IMPLEMENTED:= - date
** =:ID:= - Unique reference id of a requirement
** =:USES:= - the lemmas a theorem uses (old files: =:NEEDS:=)
** =:PROVES:= - on a proof: the conjectures it proves
** =:TEST:= - on a proof: the checks that run (old files: =:VERIFY:= on the conjecture)
** =:REVIEWED:= - date the owner last read a proven theorem against a lemma it uses that changed
* The one format
A repo opts in by putting =#+LEMMAX_TESTS:= in its requirements file; =lemmax lint= then refuses anything this section does not allow.
- A requirement is a conjecture: a heading with a state, =** CONJECTURE [#A] Title  :tag:=; the heading text carries no id.
- Its states are =CONJECTURE | LEMMA THEOREM REFUTED=. Old files keep =OPEN | DONE DROPPED= until =lemmax migrate= moves them.
- A proof is a heading in =FILE.proofs.org=, beside the conjectures, never a child of one; its states are =OPEN | PASSED=.
- A proof has its own =:ID:=, =:PROVES:= with the ids of the conjectures it proves, a body saying what it shows, and =:TEST:= with its test addresses.
- A conjecture may have many proofs; one proof may prove many conjectures.
- =:ID:= holds the id: a UUID v7 for a requirement made from 2026-11-21 on, as [[*A new requirement id is a UUID v7, unique everywhere][A new requirement id is a UUID v7]] says; an older one keeps its shape =[A-Z]+-[0-9]+=, as =RF-3=. Either is unique across every opted-in file of the repo.
- =:USES:= names the ids of the lemmas a theorem uses, separated by spaces; nesting is layout only. Old files call it =:NEEDS:=.
- =:TEST:= holds test addresses, quoted like shell words: =unit/store_test "process/ids are used once"=; a long list goes on =:TEST+:= lines. Old files hold them on the conjecture as =:VERIFY:= and =:VERIFY+:=.
- Dates are =:CREATED:=, =:LAST_EDITED:=, =:APPROVED:=, =:IMPLEMENTED:= and =:REVIEWED:=, as =2026-11-15=.
- A requirement's text is its statement: heading, body and properties, all but the dates and =:VERIFY:=. A proof that changes leaves the statement as it was.
** The requirements file names the repo's tests and code
- =#+LEMMAX_TESTS: <command>= prints every test address, one per line, in the words =regress --only= takes.
- =#+LEMMAX_CODE: <paths>= names the paths whose commits must name an id, as =core/ apps/ script/=.
- A repo without =#+LEMMAX_TESTS:= keeps its own checks until it migrates.
** A suspect theorem is read again
A proven theorem is suspect when a lemma it uses changed its text after the theorem's =:IMPLEMENTED:= or =:REVIEWED:= date, whichever is later.
- The owner reads the theorem against the changed lemma, then sets =:REVIEWED:= to that day, or makes it CONJECTURE when it no longer holds.
- =lemmax trace= lists every suspect child.
* Verification requirement item
This will be child of a design requirement item explaining how it is verified
* Design requirement item
Any new design idea must have this requiremen item.
* As the requirements file is developed. During sensible time it must be split and follow a strict hierarchy.

* Requirement types
** Hard Requirements: This requirement must always be needed
** Soft Requirements: This requirement needed but flexible
** Optional Rquirement: This requirement may or may not be needed
* Process
Every change to what the app does is a requirement first; the code follows it, and the docs follow the code.
=Conjecture -> approved -> built -> proofs PASSED -> docs -> LEMMA=; an issue found while building goes back to approval.
** The workflow is called Lemmax
agent1's requirement workflow has a name: Lemmax, from "lemma". In mathematics a lemma is a small proven step used to build bigger results.
=Conjecture -> approved -> built -> proofs PASSED -> docs -> LEMMA=, every step traced by id.
Conjecture + proof = lemma. The names are the files' own words, not only an explanation.
| Mathematics    | Lemmax                                                               |
|----------------+----------------------------------------------------------------------|
| Axiom          | an agent1 rule: where every project starts, never proven             |
| Definition     | a glossary term a conjecture uses, never proven                      |
| Conjecture     | a requirement not yet proven: statement, ideas, design; =CONJECTURE= |
| Proof          | a heading in =FILE.proofs.org=: =:PROVES:= ids, =:TEST:= its tests   |
| Lemma          | a conjecture whose every proof is PASSED; =LEMMA=                    |
| Theorem        | a bigger conjecture that =:USES:= lemmas, proven too; =THEOREM=      |
| Corollary      | a project's requirement that =:FOLLOWS:= an agent1 rule              |
| Counterexample | a failing proof test: the proof is OPEN, its lemma CONJECTURE again  |
| Refuted        | a conjecture disproven or given up, kept saying why; =REFUTED=       |
| Q.E.D.         | =PASSED= on the last proof, then =LEMMA= or =THEOREM=                |
- A conjecture becomes a lemma only when it has a proof and every proof of it is PASSED.
- A theorem is proven only when its own proofs pass and every lemma it uses is proven.
- A failing proof test is a counterexample: its proof goes OPEN, and the lemma goes back to CONJECTURE until it passes; only the owner makes a conjecture REFUTED.
- A project that follows these rules "follows Lemmax".

- Named on 2026-11-21. A web search that day found no "Lemmax"; Lemax, one m, is a travel-booking software company.
** Every change starts as a requirement
An idea that changes what the app does, shows or stores becomes a conjecture at once; there is no other inbox.
- Chores that change no behaviour live in a notes file.
- Every app commit names the requirement it builds: =(S-8)=.
- A =commit-msg= hook refuses a source or test commit that names no existing id.
** Feasibility first
A requirement is written only after concrete evidence shows it can be built and tested in the project's languages and libraries.
- Evidence is one of: library docs, code already in the repo, a throwaway spike that ran, a known working example.
- A proof's =:TEST:= names a check the project can run today, or one its test tools can run once written.
- An idea that cannot be built as asked goes back to the owner with alternatives and their trade-offs; the owner picks.
- The evidence goes in the requirement as one =Evidence:= line with links.
- The idea is checked against existing requirements for duplicates and conflicts; =:USES:= names the lemmas it builds on.
- The [[file:../skills/add-requirement/SKILL.md][add-requirement]] skill follows this.
** The owner approves a requirement before it is built
A new or edited requirement is drafted, shown to the owner, and built only after their yes.
- For visual work a mockup is approved with the requirement, never as part of a proof.
- On approval it is committed, still CONJECTURE, before any code; =:APPROVED:= holds the date of the yes.
- A check refuses a LEMMA or THEOREM with no =:APPROVED:= date.
** Issues found while building come back
Building stops and the issue goes back to the owner when the requirement is wrong, ambiguous, in conflict or cannot be built.
- It is edited, approved again, and building resumes; an edited conjecture stays CONJECTURE until it has a new =:APPROVED:= date.
- A detail it is silent on, such as a name or a spacing, is decided while building and added to it in the same change.
** A lemma changes in place
Changing what a LEMMA or THEOREM says keeps its id, edits its text, and makes it CONJECTURE until the change is proven.
- A dated line says what changed: =Changed on <date>: <what>.=
- An id is never reused; a conjecture disproven or given up is REFUTED and kept, saying why.
- A =pre-commit= hook refuses a changed lemma text that is not made CONJECTURE, and a check refuses an id used twice.
** A proof is automated
Every proof's =:TEST:= names checks that run: unit tests, window checks or acceptance checks.
- No dev session, look or approval counts; a proof that has one is OPEN, and its conjecture CONJECTURE, until that part is a check.
- A check refuses a LEMMA or THEOREM with no proof or with a proof not PASSED, and a PASSED proof whose =:TEST:= is empty.
** LEMMA means built, proven and in the docs
A conjecture is a LEMMA (or THEOREM) when it is built, every proof of it is PASSED, and the docs say what changed in the design ([[file:docs.org::*Requirements and the docs][Requirements and the docs]]).
- One commit then marks its proofs PASSED and it LEMMA.
- A check refuses a PASSED proof whose =:TEST:= names a test the app repo does not have.
** Every requirement carries its dates
Three dates, as =2026-11-09=: =:CREATED:= the day it was added, =:LAST_EDITED:= the day of its last change of any kind, =:IMPLEMENTED:= the day it turned LEMMA or THEOREM.
- Only a LEMMA or THEOREM has =:IMPLEMENTED:=, the day it was proven; a proof never has one; a check refuses any other, and a missing date.
- A commit that leaves a date wrong is refused, naming the requirement and the date; nothing fills them in on its own.
- A change to a date is a change like any other.
** A project maps an agent1 requirement before it builds it
A project never builds an agent1 requirement straight from agent1. It first writes its own requirement that names the agent1 one, and builds that.
- The project's requirement carries =:FOLLOWS:= with the agent1 file and id, as =agent1/requirements/testing.org::build-test-alongside=, and a link to it in its body
- Its body says the project's part only: which files, commands and checks; the general rule is linked, never copied
- Its proofs' =:TEST:= names the project's own checks
- Commits name the project's id, never the agent1 id
- When the agent1 requirement changes, every project requirement that follows it is suspect until read again, as a changed parent makes its children suspect
- A project that does not adopt an agent1 requirement writes nothing; agent1 rules are opt-in per project
- Why: so each project can show which agent1 rules it follows, how, and since when

** A new requirement id is a UUID v7, unique everywhere
Every requirement id is unique across every project, so a link or a commit can never name the wrong one.
- A new requirement's =:ID:= is a UUID v7 (RFC 9562), lower case with hyphens, as =01a1fe0b-58fc-7462-bad3-1df76777aa8e=: the first 12 hex digits the time it was made in milliseconds, the rest random
- It is made by a tool (=python3 -c 'import uuid; print(uuid.uuid7())'=, Python 3.14 and later), never typed or picked by hand; it needs no check against other ids
- Ids that exist today keep their shape forever: =M-12=, =RT-3=, =touch-gesture-map=; an id is never renamed or reused
- A heading names its requirement in words; the id is for links, =:USES:=, =:PROVES:=, =:FOLLOWS:= and commits
- In a commit message, an id may be cut to its last 12 hex digits when that is unique among every id in =~/repos=
- Why: on 2026-11-21 two sessions each gave a new requirement the id RT-17, and Arcadia held two M-11s; ids counted up per project clash when sessions write at once
Evidence: Python 3.15.2 on this Mac printed =01a1fe0b-58fc-7462-bad3-1df76777aa8e= from =uuid.uuid7()=.
