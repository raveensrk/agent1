* Each Requirement must be an org mode heading
* A requirement file can be 1 file or multiple files
* Requirements can be scheduled.
If a requirement is written but becomes valid only after 2 weeks. =:SCHEDULED:= Property.
* Data format = =YYYY-MM-DD=
* Properties
Properties are optional for a small design. For larger design the following fields becomes mandatory.
** =:CREATED:= - date
** =:LAST_EDITED:= - date
** =:APPROVED:= - date
** =:IMPLEMENTED:= - date
** =:NEEDS:= - Parent requirement link
** =:ID:= - Unique reference id of a requirement
** =:VERIFY:= - Names the checks that run
** =:REVIEWED:= - date the owner last read a DONE child against its changed parent
* The one format
A repo opts in by putting =#+REQTRACE_TESTS:= in its requirements file; =reqtrace lint= then refuses anything this section does not allow.
- A requirement is a heading with a state, =** OPEN [#A] Title  :tag:=; the heading text carries no id.
- =:ID:= holds the id: a UUID v7 for a requirement made from 2026-11-21 on, as [[*A new requirement id is a UUID v7, unique everywhere][A new requirement id is a UUID v7]] says; an older one keeps its shape =[A-Z]+-[0-9]+=, as =RF-3=. Either is unique across every opted-in file of the repo.
- =:NEEDS:= names one or more parent ids, separated by spaces; nesting is layout only.
- =:VERIFY:= holds test addresses, quoted like shell words: =unit/store_test "process/ids are used once"=; a long list goes on =:VERIFY+:= lines.
- Dates are =:CREATED:=, =:LAST_EDITED:=, =:APPROVED:=, =:IMPLEMENTED:= and =:REVIEWED:=, as =2026-11-15=.
- A requirement's text is its heading, body and properties, all but the dates.
** The requirements file names the repo's tests and code
- =#+REQTRACE_TESTS: <command>= prints every test address, one per line, in the words =regress --only= takes.
- =#+REQTRACE_CODE: <paths>= names the paths whose commits must name an id, as =core/ apps/ script/=.
- A repo without =#+REQTRACE_TESTS:= keeps its own checks until it migrates.
** A suspect child is read again
A DONE child is suspect when a parent's text changed after the child's =:IMPLEMENTED:= or =:REVIEWED:= date, whichever is later.
- The owner reads the child against the changed parent, then sets =:REVIEWED:= to that day, or makes the child OPEN when it no longer holds.
- =reqtrace trace= lists every suspect child.
* Verification requirement item
This will be child of a design requirement item explaining how it is verified
* Design requirement item
Any new design idea must have this requiremen item.
* As the requirements file is developed. During sensible time it must be split and follow a strict hierarchy.
* =Tags= and =priorities= can be use to organize and prioritize.
Priorites: A, B, C.
Tags: As needed
* Requirement types
** Hard Requirements: This requirement must always be needed
** Soft Requirements: This requirement needed but flexible
** Optional Rquirement: This requirement may or may not be needed
* Process
Every change to what the app does is a requirement first; the code follows it, and the docs follow the code.
=Idea -> requirement -> approved -> built -> verified -> docs -> DONE=; an issue found while building goes back to approval.
** Every change starts as a requirement
An idea that changes what the app does, shows or stores becomes an OPEN requirement at once; there is no other inbox.
- Chores that change no behaviour live in a notes file.
- Every app commit names the requirement it builds: =(S-8)=.
- A =commit-msg= hook refuses a source or test commit that names no existing id.
** Feasibility first
A requirement is written only after concrete evidence shows it can be built and tested in the project's languages and libraries.
- Evidence is one of: library docs, code already in the repo, a throwaway spike that ran, a known working example.
- =:VERIFY:= names a check the project can run today, or one its test tools can run once written.
- An idea that cannot be built as asked goes back to the owner with alternatives and their trade-offs; the owner picks.
- The evidence goes in the requirement as one =Evidence:= line with links.
- The idea is checked against existing requirements for duplicates and conflicts; =:NEEDS:= names a parent if one fits.
- The [[file:../skills/add-requirement/SKILL.md][add-requirement]] skill follows this.
** The owner approves a requirement before it is built
A new or edited requirement is drafted, shown to the owner, and built only after their yes.
- For visual work a mockup is approved with the requirement, never as part of =:VERIFY:=.
- On approval it is committed, still OPEN, before any code; =:APPROVED:= holds the date of the yes.
- A check refuses an OPEN requirement with no =:APPROVED:= date.
** Issues found while building come back
Building stops and the issue goes back to the owner when the requirement is wrong, ambiguous, in conflict or cannot be built.
- It is edited, approved again, and building resumes; an edited requirement is OPEN until it has a new =:APPROVED:= date.
- A detail it is silent on, such as a name or a spacing, is decided while building and added to it in the same change.
** A DONE requirement changes in place
Changing what a DONE requirement says keeps its id, edits its text, and makes it OPEN until the change is built.
- A dated line says what changed: =Changed on <date>: <what>.=
- An id is never reused; a requirement given up is DROPPED and kept, saying why.
- A =pre-commit= hook refuses a changed DONE text that is not made OPEN, and a check refuses an id used twice.
** VERIFY is automated
Every =:VERIFY:= names checks that run: unit tests, window checks or acceptance checks.
- No dev session, look or approval counts; a requirement whose =:VERIFY:= has one is OPEN until that part is a check.
- A check refuses a DONE requirement whose =:VERIFY:= names no check, or asks for one of those.
** DONE means built, verified and in the docs
A requirement is DONE when it is built, every check its =:VERIFY:= names passes, and the docs say what changed in the design ([[file:docs.org::*Requirements and the docs][Requirements and the docs]]).
- One commit then marks it DONE.
- A check refuses a DONE requirement whose =:VERIFY:= names a test the app repo does not have.
** Every requirement carries its dates
Three dates, as =2026-11-09=: =:CREATED:= the day it was added, =:LAST_EDITED:= the day of its last change of any kind, =:IMPLEMENTED:= the day it turned DONE.
- Only a DONE requirement has =:IMPLEMENTED:=; a check refuses any other, and a missing date.
- A commit that leaves a date wrong is refused, naming the requirement and the date; nothing fills them in on its own.
- A change to a date is a change like any other.
** A project maps an agent1 requirement before it builds it
A project never builds an agent1 requirement straight from agent1. It first writes its own requirement that names the agent1 one, and builds that.
- The project's requirement carries =:FOLLOWS:= with the agent1 file and id, as =agent1/requirements/testing.org::build-test-alongside=, and a link to it in its body
- Its body says the project's part only: which files, commands and checks; the general rule is linked, never copied
- Its =:VERIFY:= names the project's own checks
- Commits name the project's id, never the agent1 id
- When the agent1 requirement changes, every project requirement that follows it is suspect until read again, as a changed parent makes its children suspect
- A project that does not adopt an agent1 requirement writes nothing; agent1 rules are opt-in per project
- Why: so each project can show which agent1 rules it follows, how, and since when

** A new requirement id is a UUID v7, unique everywhere
Every requirement id is unique across every project, so a link or a commit can never name the wrong one.
- A new requirement's =:ID:= is a UUID v7 (RFC 9562), lower case with hyphens, as =01a1fe0b-58fc-7462-bad3-1df76777aa8e=: the first 12 hex digits the time it was made in milliseconds, the rest random
- It is made by a tool (=python3 -c 'import uuid; print(uuid.uuid7())'=, Python 3.14 and later), never typed or picked by hand; it needs no check against other ids
- Ids that exist today keep their shape forever: =M-12=, =RT-3=, =touch-gesture-map=; an id is never renamed or reused
- A heading names its requirement in words; the id is for links, =:NEEDS:=, =:FOLLOWS:= and commits
- In a commit message, an id may be cut to its last 12 hex digits when that is unique among every id in =~/repos=
- Why: on 2026-11-21 two sessions each gave a new requirement the id RT-17, and Arcadia held two M-11s; ids counted up per project clash when sessions write at once
Evidence: Python 3.15.2 on this Mac printed =01a1fe0b-58fc-7462-bad3-1df76777aa8e= from =uuid.uuid7()=.
